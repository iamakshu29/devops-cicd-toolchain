# 09 — Notifications: Slack / Teams Build Alerts

> Your pipeline is useless if nobody knows when it fails.
> Notifications are the last thing to add and the first thing people notice is missing.

---

## What It Is + Why It Matters

Notification integration sends a message to Slack or Teams when a Jenkins build completes — passing or failing. This is not a security or quality gate; it is the feedback loop that makes the pipeline operationally useful.

**Why it belongs in the pipeline:** When a build fails at 2am due to a Trivy finding on a base image update, the on-call engineer needs to know immediately. Polling Jenkins manually is not a real operational practice.

---

## How It Works

```
Jenkins Pipeline
      │
      └── post { success { ... } failure { ... } always { ... } }
                     │
                     ▼
             slackSend() or sh 'curl -X POST ...'
                     │
                     │  HTTP POST to Slack Incoming Webhook URL
                     │  or Teams Incoming Webhook URL
                     │
                     ▼
             Slack / Teams channel receives the message
```

Two implementation options:
1. **Slack Notification Plugin** — cleaner syntax, rich formatting, supports threading
2. **curl with webhook URL** — works for both Slack and Teams, no plugin needed, portable

---

## Option A — Slack (via Plugin)

### Step 1 — Create a Slack App and Get Webhook URL
1. Go to: `https://api.slack.com/apps` → Create New App → From scratch
2. Name it `Jenkins CI`, select your workspace
3. In the app settings: **Incoming Webhooks** → turn On → **Add New Webhook to Workspace**
4. Pick the channel (e.g. `#deployments`)
5. Copy the webhook URL: `https://hooks.slack.com/services/T000/B000/xxx`

### Step 2 — Store Webhook in Jenkins
1. **Manage Jenkins** → **Credentials** → **System** → **Global credentials**
2. Add credential:
   - Kind: **Secret text**
   - Secret: the webhook URL
   - ID: `slack-webhook`

### Step 3 — Install Plugin
1. **Manage Jenkins** → **Plugins** → **Available plugins**
2. Search: `Slack Notification`
3. Install

### Step 4 — Configure Plugin
1. **Manage Jenkins** → **System** → scroll to **Slack**
   - Workspace: your Slack workspace name
   - Credential: select `slack-webhook`
   - Default channel: `#deployments`
2. Click **Test Connection** → you should see a test message in Slack
3. Save

---

## Option B — curl with Webhook (No Plugin — Works for Slack and Teams)

No plugin or Jenkins configuration needed. Just store the webhook URL as a credential and call it with curl.

Store the webhook URL in Jenkins as a Secret Text credential with ID `slack-webhook`.

## The Jenkinsfile `post` Block

### Using the Slack Plugin:

```groovy
// Generated by GitHub Copilot
post {
    success {
        slackSend(
            channel: '#deployments',
            color: 'good',
            message: """
                *BUILD PASSED* :white_check_mark:
                Job: `${env.JOB_NAME}`
                Build: `#${env.BUILD_NUMBER}`
                Branch: `${env.GIT_BRANCH}`
                Duration: ${currentBuild.durationString}
                <${env.BUILD_URL}|View Build>
            """.stripIndent()
        )
    }
    failure {
        slackSend(
            channel: '#deployments',
            color: 'danger',
            message: """
                *BUILD FAILED* :x:
                Job: `${env.JOB_NAME}`
                Build: `#${env.BUILD_NUMBER}`
                Branch: `${env.GIT_BRANCH}`
                Failed Stage: `${env.STAGE_NAME}`
                <${env.BUILD_URL}console|View Console Log>
            """.stripIndent()
        )
    }
    unstable {
        slackSend(
            channel: '#deployments',
            color: 'warning',
            message: """
                *BUILD UNSTABLE* :warning:
                Job: `${env.JOB_NAME}` | Build `#${env.BUILD_NUMBER}`
                <${env.BUILD_URL}|View Build>
            """.stripIndent()
        )
    }
}
```

### Using curl (Plugin-free, works for Slack and Teams):

```groovy
post {
    success {
        withCredentials([string(credentialsId: 'slack-webhook', variable: 'WEBHOOK')]) {
            sh """
                curl -s -X POST ${WEBHOOK} \
                  -H 'Content-type: application/json' \
                  --data '{
                    "text": "BUILD PASSED :white_check_mark: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                    "attachments": [{
                      "color": "good",
                      "text": "<${env.BUILD_URL}|View Build>"
                    }]
                  }'
            """
        }
    }
    failure {
        withCredentials([string(credentialsId: 'slack-webhook', variable: 'WEBHOOK')]) {
            sh """
                curl -s -X POST ${WEBHOOK} \
                  -H 'Content-type: application/json' \
                  --data '{
                    "text": "BUILD FAILED :x: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                    "attachments": [{
                      "color": "danger",
                      "text": "<${env.BUILD_URL}console|View Console Log>"
                    }]
                  }'
            """
        }
    }
}
```

## `post` Block Conditions — Know All of Them

| Condition | When it runs |
|-----------|-------------|
| `always` | Always, regardless of result |
| `success` | Only when build succeeded |
| `failure` | Only when build failed |
| `unstable` | Only when build is unstable (test failures but no error) |
| `changed` | Only when result is different from the previous build |
| `fixed` | Only when the previous build was failing and this one succeeded |
| `regression` | Only when the previous build was passing and this one failed |
| `aborted` | Only when build was manually aborted |
| `cleanup` | Always runs last, even if earlier post conditions throw errors |

**`fixed` and `regression` are the most useful for a production pipeline** — they alert only when state changes, not on every build. This prevents alert fatigue from a build that is consistently failing.

```groovy
post {
    regression {
        slackSend channel: '#deployments', color: 'danger',
                  message: "NEWLY BROKEN: ${env.JOB_NAME} #${env.BUILD_NUMBER} | <${env.BUILD_URL}|View>"
    }
    fixed {
        slackSend channel: '#deployments', color: 'good',
                  message: "FIXED: ${env.JOB_NAME} #${env.BUILD_NUMBER} | <${env.BUILD_URL}|View>"
    }
}
```

## Verification

After pushing a commit that triggers the pipeline:
1. Check the Slack `#deployments` channel for the message
2. Verify the build URL link in the message works
3. Intentionally break the build (add a syntax error to a file) and verify the failure notification arrives

---

## Common Errors + Debugging

### 1. `slackSend: No such DSL method`
**Cause:** Slack Notification plugin is not installed
**Fix:** Install the plugin from Manage Jenkins → Plugins

### 2. Message sends but shows as plain text with no formatting
**Cause:** Using regular quotes instead of backticks in the Slack message — Slack markdown requires backticks for code formatting
**Fix:** The Slack message format uses `*bold*`, `_italic_`, and `` `code` `` — not standard Markdown

### 3. `403 Forbidden` on webhook URL
**Cause:** Webhook URL was rotated or revoked in Slack
**Fix:** Generate a new webhook URL in the Slack app settings and update the Jenkins credential

### 4. Build URL in message is `http://localhost:8080/...` — not clickable from Slack
**Cause:** Jenkins `Jenkins URL` configuration uses localhost
**Fix:** **Manage Jenkins** → **System** → **Jenkins URL** → set to the actual reachable URL (your server's IP or domain, e.g., `http://192.168.1.10:8080/`)

## Break It on Purpose

**1. Use a revoked or wrong webhook URL**
Change the `slack-webhook` credential to a garbage URL: `https://hooks.slack.com/services/FAKE/FAKE/FAKE`.
Run the pipeline. Observe: the `slackSend` step does not throw an error — it silently fails with HTTP 400/403. Jenkins build still shows green.
Check the build log for: `Response: Status code 400` or look for no error at all.
This is why you must test notifications separately — a broken webhook does not fail the pipeline.
Fix: restore the correct webhook URL and verify by running the Slack plugin's **Test Connection** in Jenkins System config.

**2. Jenkins URL not configured — links are broken**
In Jenkins: Manage Jenkins → System → Jenkins URL → set it to `http://localhost:8080`.
Send a notification. Open the Slack message and click the build link.
The link goes to `http://localhost:8080/...` — unreachable from Slack.
Fix: set Jenkins URL to the actual server IP or hostname: `http://192.168.x.x:8080/` or your domain.

**3. Use `failure` instead of `regression` — observe alert fatigue**
Set up your post block to use `failure` for notifications.
Break a test intentionally so the build fails consistently.
Run the pipeline 5 times. Count the Slack messages you receive.
Now switch to `regression` + `fixed`. Break the same test, run it 5 times again.
Compare the number of Slack messages.
This is why `regression`/`fixed` are the right conditions for production pipelines.

## Complete Final Pipeline Snapshot (All Tools — After This Step)

```groovy
// Generated by GitHub Copilot
pipeline {
    agent any

    environment {
        NEXUS_REGISTRY  = 'nexus:8082'
        IMAGE_NAME      = "${NEXUS_REGISTRY}/sample-app"
        IMAGE_TAG       = "${env.BUILD_NUMBER}"
        SONAR_PROJECT   = 'sample-app'
    }

    stages {

        stage('Checkout') {
            steps {
                git branch: 'main', url: 'https://github.com/your-org/sample-app.git'
            }
        }

        stage('Checkov — IaC Scan') {
            steps {
                sh 'checkov -d terraform/ --framework terraform --compact --soft-fail'
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package -DskipTests'
            }
        }

        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('SonarQube') {
                    sh "mvn sonar:sonar -Dsonar.projectKey=${SONAR_PROJECT}"
                }
            }
        }

        stage('Quality Gate') {
            steps {
                timeout(time: 5, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }

        stage('OWASP Dependency Check') {
            steps {
                dependencyCheck additionalArguments: '--scan ./ --format XML',
                                odcInstallation: 'Dependency-Check'
                dependencyCheckPublisher pattern: 'dependency-check-report.xml',
                                         failedTotalCritical: 1
            }
        }

        stage('Docker Build') {
            steps {
                sh "docker build -t ${IMAGE_NAME}:${IMAGE_TAG} ."
            }
        }

        stage('Trivy — Image Scan') {
            steps {
                sh """
                    trivy image \
                      --exit-code 1 \
                      --severity HIGH,CRITICAL \
                      --ignore-unfixed \
                      ${IMAGE_NAME}:${IMAGE_TAG}
                """
            }
        }

        stage('Push to Nexus') {
            steps {
                script {
                    docker.withRegistry("http://${NEXUS_REGISTRY}", 'nexus-credentials') {
                        docker.image("${IMAGE_NAME}:${IMAGE_TAG}").push()
                        docker.image("${IMAGE_NAME}:${IMAGE_TAG}").push('latest')
                    }
                }
            }
        }

        stage('Cosign — Sign Image') {
            steps {
                withCredentials([
                    file(credentialsId: 'cosign-private-key', variable: 'COSIGN_KEY'),
                    string(credentialsId: 'cosign-key-password', variable: 'COSIGN_PASSWORD')
                ]) {
                    sh """
                        COSIGN_PASSWORD=${COSIGN_PASSWORD} \
                        cosign sign --key ${COSIGN_KEY} --yes \
                          --allow-insecure-registry \
                          ${IMAGE_NAME}:${IMAGE_TAG}
                    """
                }
            }
        }

        stage('Update GitOps Repo') {
            steps {
                withCredentials([usernamePassword(credentialsId: 'github-credentials',
                                                   usernameVariable: 'GIT_USER',
                                                   passwordVariable: 'GIT_TOKEN')]) {
                    sh """
                        git clone https://${GIT_USER}:${GIT_TOKEN}@github.com/your-org/gitops-repo.git
                        cd gitops-repo
                        sed -i 's|image: .*|image: ${IMAGE_NAME}:${IMAGE_TAG}|' k8s/deployment.yaml
                        git config user.email "jenkins@ci.local"
                        git config user.name "Jenkins"
                        git commit -am "ci: update image tag to ${IMAGE_TAG}"
                        git push
                    """
                }
            }
        }
    }

    post {
        regression {
            slackSend channel: '#deployments', color: 'danger',
                      message: "NEWLY BROKEN: ${env.JOB_NAME} #${env.BUILD_NUMBER} | <${env.BUILD_URL}|View>"
        }
        fixed {
            slackSend channel: '#deployments', color: 'good',
                      message: "FIXED: ${env.JOB_NAME} #${env.BUILD_NUMBER} | <${env.BUILD_URL}|View>"
        }
        failure {
            slackSend channel: '#deployments', color: 'danger',
                      message: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER} | <${env.BUILD_URL}|View>"
        }
    }
}
```

## Interview Questions

**Q: Where does notification logic go in a Jenkinsfile and why?**
A: In the `post` block, outside the `stages` block. The `post` block runs after all stages complete regardless of whether a stage failed. Putting notifications in a stage would mean they only run if all previous stages passed.

**Q: How do you avoid alert fatigue from build notifications?**
A: Use `regression` and `fixed` conditions instead of `failure` and `success`. `regression` fires only when a previously passing build starts failing, and `fixed` fires only when a failing build recovers. This eliminates notifications on every build and alerts only when state changes.

**Q: How do you securely pass the Slack webhook URL to the curl command in Jenkins?**
A: Store the webhook URL as a Secret Text credential in Jenkins and reference it using `withCredentials([string(credentialsId: 'slack-webhook', variable: 'WEBHOOK')])`. The URL is injected at runtime and masked in the build logs — it never appears in the Jenkinsfile source code.
