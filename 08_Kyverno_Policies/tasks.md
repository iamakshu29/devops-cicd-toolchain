# 08 — Kyverno: Kubernetes Policy Enforcement

> Not a pipeline stage. Not a CLI tool you install on Jenkins.
> Kyverno is a Kubernetes admission controller — it enforces cluster-wide rules every time any resource is created or updated, regardless of who or what is deploying.

---

## What It Is + Why It Matters

Kyverno is a **policy engine** for Kubernetes. You define rules as `ClusterPolicy` YAML manifests (standard K8s resources). Kyverno registers itself as an admission webhook — Kubernetes calls it before admitting any new resource. If a resource violates a policy, Kubernetes rejects it.

**Why it matters in your pipeline context:**
Even if Jenkins runs every scan and everything passes, someone could still `kubectl apply` a deployment manually that runs as root, or pull an image from Docker Hub bypassing Nexus. Kyverno prevents this at the cluster level, not the pipeline level. It is the last line of defense.

**What you already know:** You have written Kyverno ClusterPolicy manifests in K8s Task-05 (RBAC and Security). What this section adds is how Kyverno fits into the pipeline workflow and what policies you write specifically for a CI/CD context.

---

## Kyverno's Three Modes

| Mode | What it does |
|------|-------------|
| `Enforce` | Hard block — resource is rejected, pod never starts |
| `Audit` | Soft block — resource is allowed but a policy report is generated, violation is logged |
| `generate` | Creates additional resources automatically when a new resource matches (e.g., create a NetworkPolicy whenever a new namespace is created) |

**Start with `Audit` when introducing policies to an existing cluster.** It lets you see what would be blocked without actually blocking anything. Switch to `Enforce` after reviewing the audit reports.

## How It Fits Into the Pipeline

```
Jenkins pipeline completes → image signed with Cosign → GitOps repo updated with new image tag
                                                              │
                                                              ▼
                                                        ArgoCD syncs
                                                              │
                                                              ▼
                                           K8s API receives new Pod/Deployment spec
                                                              │
                                                              ▼
                                           Kyverno admission webhook intercepts the request
                                                              │
                                           ┌─────────────────┴─────────────────────┐
                                           │                                         │
                                    Policy checks pass                      Policy check fails
                                           │                                         │
                                           ▼                                         ▼
                                    Pod is admitted                     Pod is rejected (Enforce mode)
                                    Pod starts running                  ArgoCD sync fails with error
```

## Infrastructure Setup

### Install Kyverno via Helm

```bash
helm repo add kyverno https://kyverno.github.io/kyverno/
helm repo update

helm install kyverno kyverno/kyverno \
  --namespace kyverno \
  --create-namespace

# Verify Kyverno is running
kubectl -n kyverno get pods
# Should show: kyverno-xxx   1/1   Running
```

Kyverno automatically registers its mutating and validating admission webhooks on install.

## The Policies Folder Structure

Policies live in a `policies/` directory in your GitOps repo (or app repo). ArgoCD applies them to the cluster.

```
gitops-repo/
  policies/
    require-resource-limits.yaml
    block-root-containers.yaml
    enforce-nexus-registry.yaml
    verify-cosign-signature.yaml
  k8s/
    deployment.yaml
    service.yaml
```

ArgoCD Application for policies:
```yaml
# Generated by GitHub Copilot
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: cluster-policies
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/gitops-repo
    targetRevision: HEAD
    path: policies/
  destination:
    server: https://kubernetes.default.svc
    namespace: kyverno   # or default — ClusterPolicy is cluster-scoped anyway
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

## Essential Policies for a CI/CD Pipeline Context

### Policy 1 — Block containers running as root

```yaml
# Generated by GitHub Copilot
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: block-root-containers
  annotations:
    policies.kyverno.io/description: >
      Prevents containers from running as root (UID 0).
      runAsNonRoot must be set to true in the securityContext.
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-runAsNonRoot
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Containers must not run as root. Set securityContext.runAsNonRoot: true"
        pattern:
          spec:
            containers:
              - securityContext:
                  runAsNonRoot: true
```

### Policy 2 — Require resource limits on all containers

```yaml
# Generated by GitHub Copilot
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
  annotations:
    policies.kyverno.io/description: >
      All containers must have CPU and memory limits defined.
      Prevents a single pod from starving the node.
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-resource-limits
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "CPU and memory limits must be set on all containers"
        pattern:
          spec:
            containers:
              - resources:
                  limits:
                    memory: "?*"
                    cpu: "?*"
```

### Policy 3 — Enforce images come from Nexus only

```yaml
# Generated by GitHub Copilot
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: enforce-nexus-registry
  annotations:
    policies.kyverno.io/description: >
      All container images must be pulled from the internal Nexus registry.
      Prevents pods from pulling from Docker Hub or other external registries.
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-registry
      match:
        any:
          - resources:
              kinds: [Pod]
              namespaces: ["default", "production", "staging"]   # exclude kube-system
      validate:
        message: "Images must be pulled from nexus:8082. External registries are not allowed."
        pattern:
          spec:
            containers:
              - image: "nexus:8082/*"
```

### Policy 4 — Verify Cosign image signature

```yaml
# Generated by GitHub Copilot
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
  annotations:
    policies.kyverno.io/description: >
      Verifies that all sample-app images have a valid Cosign signature.
      Rejects pods whose images were not signed by the CI/CD pipeline.
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-cosign-signature
      match:
        any:
          - resources:
              kinds: [Pod]
      verifyImages:
        - imageReferences:
            - "nexus:8082/sample-app:*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      <paste your cosign.pub contents here>
                      -----END PUBLIC KEY-----
```

## Common Errors + Debugging

### 1. ArgoCD sync fails with `resource denied by Kyverno`
**Cause:** A policy in `Enforce` mode is blocking the deployment
**Debug:** `kubectl describe pod <pod>` → Events section shows which Kyverno rule denied it
**Fix:** Either fix the deployment manifest to comply with the policy, or if the policy is wrong, update it

### 2. Policy is applied but violations still get through
**Cause 1:** Policy is in `Audit` mode not `Enforce`
**Cause 2:** The namespace is excluded from the policy's `match` criteria
**Cause 3:** The resource kind is not `Pod` but `Deployment` — Kyverno checks Pod specs, and Deployments create Pods. Check your `match.any.resources.kinds` — use `[Pod]` not `[Deployment]` for container-level checks.

### 3. Kyverno is blocking `kube-system` pods on startup
**Cause:** Policy `match` criteria too broad — applies to all namespaces including `kube-system`
**Fix:** Add namespace exclusions to your policy:
```yaml
match:
  any:
    - resources:
        kinds: [Pod]
        namespaces: ["default", "production"]   # list only your app namespaces
```
Or use `exclude`:
```yaml
exclude:
  any:
    - resources:
        namespaces: ["kube-system", "kyverno", "argocd", "vault"]
```

### 4. `verifyImages` policy not blocking unsigned images
**Cause 1:** Nexus is HTTP and `allowInsecureRegistry` is not set in the policy
**Cause 2:** Kyverno cannot reach Nexus due to a NetworkPolicy
**Fix:** Add to the `verifyImages` entry: `repository: nexus:8082` and ensure network access from Kyverno pods to Nexus

## Break It on Purpose

**1. Apply block-root-containers in Enforce mode, then deploy a non-compliant pod**
Apply the `block-root-containers` ClusterPolicy.
Then try to deploy a pod that does NOT set `runAsNonRoot`:
```bash
kubectl run test-root --image=nginx --restart=Never
```
Observe: `Error from server: admission webhook "mutate.kyverno.svc" denied the request: Containers must not run as root.`
Now fix the deployment (add `securityContext.runAsNonRoot: true`) and retry.

**2. Apply enforce-nexus-registry, then deploy nginx from Docker Hub**
Apply the `enforce-nexus-registry` ClusterPolicy.
Then try: `kubectl run test-hub --image=nginx:latest --restart=Never`
Observe: rejected. The image `nginx:latest` does not start with `nexus:8082/`.
This is the policy working exactly as intended.

**3. Apply policies without excluding system namespaces**
Apply `block-root-containers` WITHOUT the namespace exclusion for `kube-system`.
Check what happens to existing kube-system pods: `kubectl get pods -n kube-system`
Existing pods are not affected (Kyverno only validates new/updated resources). But try to delete and let Kubernetes recreate a kube-system pod — it may be blocked.
Fix: add the `exclude` block with `kube-system`, `kyverno`, `argocd`, `vault` before going to Enforce mode.

## Scenario — Multiple Policies Breaking an ArgoCD Sync

**Setup:** All 4 ClusterPolicies are in `Enforce` mode. ArgoCD tries to sync a new deployment.

ArgoCD sync fails. You see this in the ArgoCD UI:
```
ComparisonError: one or more objects failed to apply:
  admission webhook "mutate.kyverno.svc" denied the request
```

**Your task:** Diagnose which policy is blocking it and why.

Work through this diagnosis:
```bash
# Step 1 — try to apply the manifest manually to get the full error
kubectl apply -f k8s/deployment.yaml

# The error message will name the Kyverno rule that failed, e.g.:
#   "Containers must not run as root" → block-root-containers
#   "CPU and memory limits must be set" → require-resource-limits
#   "Images must be pulled from nexus:8082" → enforce-nexus-registry
#   "image signature verification failed" → verify-image-signature

# Step 2 — fix the violation in the manifest
# Step 3 — commit to GitOps repo, ArgoCD syncs again
```

**Scenario exercise:** Deliberately create a deployment manifest that violates ALL FOUR policies simultaneously (no securityContext, no resource limits, uses `nginx:latest`, unsigned). Apply it. Read all four rejection messages. Fix them one by one and observe which Kyverno rule each fix satisfies.

This is the real learning for Kyverno — not applying policies to a clean deployment, but diagnosing a broken one when you have multiple policies active.

## Interview Questions

**Q: What is Kyverno and how is it different from RBAC?**
A: RBAC controls WHO can do what in Kubernetes — which users/service accounts can create, read, update, or delete resources. Kyverno controls WHAT resources are allowed to exist — it validates the content of resources regardless of who created them. RBAC can prevent a developer from deploying to production, but if they have permission, Kyverno ensures the deployment itself meets policy requirements (no root containers, required resource limits, etc.).

**Q: How do you introduce Kyverno policies to an existing cluster without breaking things?**
A: Start with `validationFailureAction: Audit`. Policies log violations but do not block anything. Review the `PolicyReport` and `ClusterPolicyReport` resources to see what would be blocked. Fix violations one by one, then switch each policy to `Enforce` after the cluster is compliant. Never switch to Enforce blindly on an existing cluster.

**Q: Is Kyverno a pipeline stage or a cluster component?**
A: Cluster component. It runs as an admission webhook inside Kubernetes. It is not called from Jenkins. Once `ClusterPolicy` manifests are applied to the cluster (via ArgoCD), Kubernetes enforces them automatically at admission time for every resource creation or update, regardless of the source.

**Q: How do you exclude kube-system from Kyverno policies?**
A: Use the `exclude` block in the policy rule to list namespaces like `kube-system`, `kyverno`, `argocd`, and `vault`. Or use the `match` block to explicitly list only your application namespaces. Without exclusions, policies can block system pods and break the cluster.

**Q: How does Kyverno verify Cosign signatures?**
A: Using the `verifyImages` rule in a ClusterPolicy. You provide the public key in the policy. When a pod is admitted, Kyverno fetches the Cosign signature from the registry and verifies it against the public key. If the image has no valid signature or the signature was made with a different key, the pod is rejected.
