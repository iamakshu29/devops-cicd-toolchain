# 02 — OWASP Dependency Check: Library CVE Scanner

> Scans your application's dependencies (not source code, not the image) for known CVEs.
> Catches the Log4Shell class of vulnerabilities — a vulnerable library you included, not code you wrote.

---

## What It Is + Why It Matters

OWASP Dependency Check scans your project's **dependency manifest** (pom.xml, requirements.txt, package.json) and checks each library against the **NVD (National Vulnerability Database)** maintained by NIST. If a library version you are using has a published CVE, it reports it.

**Difference from Trivy (important for interviews):**

| Tool     | What it scans                                          | When it runs                     |
| -------- | ------------------------------------------------------ | -------------------------------- |
| OWASP DC | App library dependencies (source-level)                | After build, before Docker build |
| Trivy    | Container image (OS packages + libraries in the image) | After Docker build               |

They overlap but are not duplicates. OWASP DC catches the library earlier (before you even build an image). Trivy catches everything in the final image including OS vulnerabilities.

**Why companies use it:** Libraries are the most common attack vector. The Log4Shell vulnerability (2021) affected thousands of companies not because they wrote bad code but because they included a vulnerable version of Log4j. OWASP DC would have flagged it.

## How It Works

```
Jenkins Pipeline
      │
      ▼
OWASP Dependency Check plugin (runs on Jenkins agent)
      │
      │  1. Downloads/updates NVD vulnerability database on first run
      │     (This is a ~500MB download — first run is slow, subsequent runs use cache)
      │
      │  2. Reads dependency manifest: pom.xml / requirements.txt / package-lock.json
      │
      │  3. Resolves the exact library versions declared
      │
      │  4. Checks each library against the local NVD database copy
      │
      │  5. Generates report: dependency-check-report.xml / .html
      │
      ▼
Jenkins — dependencyCheckPublisher reads the XML report
      │
      │  6. Displays vulnerability trend graph on Jenkins job page
      │  7. Marks build UNSTABLE or FAILED based on configured thresholds
```

**No external server required.** The NVD database is downloaded locally to the Jenkins agent. This is different from SonarQube which needs a separate server.

---

## Infrastructure Setup

No separate server to run. The tool installs as a Jenkins plugin and downloads its database to the Jenkins agent's workspace.
Plugin Name - `OWASP Dependency-Check, Version:5.6.4`

**One prerequisite:** The Jenkins agent needs internet access to download the NVD database. The database is updated daily — OWASP DC re-downloads it if the local copy is older than 4 hours.

**Optional — NVD API Key:**
Since 2023, NVD rate-limits unauthenticated downloads significantly. Without an API key, the initial download can take 30+ minutes. Get a free API key at: `https://nvd.nist.gov/developers/request-an-api-key`

## Jenkins Integration

### Step 1 — Install the Plugin

1. **Manage Jenkins** → **Plugins** → **Available plugins**
2. Search: `OWASP Dependency-Check`
3. Install (requires Jenkins restart)

### Step 2 — Configure the Tool

1. **Manage Jenkins** → **Tools** → scroll to **Dependency-Check**
2. Click **Add Dependency-Check**
   - Name: `Dependency-Check` ← referenced in Jenkinsfile's `odcInstallation` parameter
   - Check **Install automatically**
   - Add Installer -> Install from github.com
3. Apply & Save

### Step 3 — (Optional) Add NVD API Key

If you have an NVD API key, add it as a Jenkins credential:

1. **Manage Jenkins** → **Credentials** → **System** → **Global credentials**
2. Add credential:
   - Kind: **Secret text**
   - Secret: your NVD API key (775d3454-dffc-49f4-9d34-7e5502adc197)
   - ID: `nvd-api-key`

Then reference it in the Jenkinsfile stage (see below).

## The Jenkinsfile Stage

```groovy
// Generated by GitHub Copilot
stage('OWASP Dependency Check') {
    steps {
        // Scans project directory; XML report is required for dependencyCheckPublisher
        dependencyCheck additionalArguments: '''
            --scan ./
            --format XML
            --format HTML
        ''', odcInstallation: 'Dependency-Check'

        // Publishes the report to Jenkins and trends the results across builds
        dependencyCheckPublisher pattern: 'dependency-check-report.xml'
    }
}
```

**With NVD API key (avoids rate limiting):**

```groovy
stage('OWASP Dependency Check') {
    steps {
        dependencyCheck(
            odcInstallation: 'Dependency-Check',
            nvdCredentialsId: 'nvd-api-key',
            additionalArguments: '''
                --scan ./
                --format XML
                --format HTML
            '''
        )

        dependencyCheckPublisher(
            pattern: 'dependency-check-report.xml'
        )
    }
}
```

**To fail the build on HIGH or CRITICAL findings:**

```groovy
dependencyCheckPublisher pattern: 'dependency-check-report.xml',
                         failedTotalCritical: 1,    // fail if any Critical CVE found
                         failedTotalHigh: 5          // fail if 5+ High CVEs found
```

### Alternative for Python

OWASP DC has limited Python support. Use `safety` or `pip-audit` instead, which are more accurate for Python:

```bash
pip install pip-audit
pip-audit -r requirements.txt --format json -o pip-audit-report.json
```

Or use OWASP DC with Python requirements file:

```bash
dependencyCheck additionalArguments: '--scan requirements.txt --enableExperimental', odcInstallation: 'Dependency-Check'
```

### Alternative for Node.js

```bash
dependencyCheck additionalArguments: '--scan package-lock.json --nodePackageSkipDevDependencies', odcInstallation: 'Dependency-Check'
```

After the pipeline runs:

2. Click the trend graph or the **Dependency Check** link in the left sidebar for the full report
3. The report shows each vulnerable library with CVE ID, severity, and a link to the CVE details

In your project workspace: `dependency-check-report.html` opens in a browser and shows a readable vulnerability report.

## Common Errors + Debugging

### 1. First run takes 30+ minutes

**Cause:** Downloading the NVD database (~500MB) for the first time. NVD rate-limits unauthenticated downloads since 2023 — without an API key, it downloads in small batches.
**Fix:** Get a free NVD API key and pass it via `--nvdApiKey`. The download then completes in under 5 minutes.

### 2. `ERROR: Unable to connect to the NVD`

**Cause:** Jenkins agent has no internet access, or firewall blocks NIST's CDN.
**Fix:** Either open the firewall or use OWASP DC in offline mode with a pre-downloaded database. In offline mode: `--noupdate` flag uses whatever database copy exists.

### 3. Report is empty / no vulnerabilities found

**Cause 1:** Scan path is wrong — `--scan ./` scans from the workspace root; if your pom.xml is in a subdirectory, adjust the path.
**Cause 2:** OWASP DC could not resolve transitive dependencies — run `mvn dependency:resolve` first to ensure all JARs are in the local Maven cache.
**Cause 3:** Using `--scan` on a Python project without `--enableExperimental` — Python support is experimental.

### 4. `dependencyCheckPublisher` fails — file not found

**Error:** `dependency-check-report.xml was not found`
**Cause:** The `dependencyCheck` step did not generate the XML format — only HTML was specified, or the step failed before generating output.
**Fix:** Always include `--format XML` in `additionalArguments`. You can include multiple formats: `--format XML --format HTML`.

### 5. Build marked UNSTABLE instead of FAILED on high-severity findings

**Cause:** Default `dependencyCheckPublisher` marks builds unstable, not failed. This is intentional — it lets you see the report without blocking the pipeline immediately.
**Fix:** Use `failedTotalCritical` and `failedTotalHigh` thresholds in `dependencyCheckPublisher` to control when builds fail vs go unstable.

---

## Break It on Purpose

**Remove `--format XML` — publisher breaks**
Change `additionalArguments` to `--scan ./ --format HTML` only.
Run the pipeline. `dependencyCheckPublisher` fails: "dependency-check-report.xml was not found."
The scan ran and produced output, but the wrong format. This teaches you that the HTML report and the XML report are separate outputs — the plugin needs XML to parse results.
Fix: always include `--format XML`.

---

**Notes (read after deciding):**

- Test-scope dependencies that do not appear in the production artifact are genuinely lower risk — but most security teams still require tracking them. Use `--suppression` with a justification rather than ignoring.
- For "no fix available" findings, OWASP DC supports a `suppression.xml` file where you document the accepted risk with a CVE ID and expiry date.
- Suppression file format:

```xml
<suppressions>
  <suppress>
    <notes>Spring Web CVE-2016-1000027 — no fix available, accepted risk reviewed 2026-08-07</notes>
    <cve>CVE-2016-1000027</cve>
    <until>2027-01-01</until>
  </suppress>
</suppressions>
```

Pass it to the scan: `--suppression suppression.xml`

## Interview Questions

**Q: What is the difference between OWASP Dependency Check and Trivy?**
A: OWASP DC scans your source-level dependencies (the libraries declared in pom.xml or requirements.txt) before a Docker image is built. Trivy scans the final container image including OS packages. They complement each other — OWASP DC catches the library earlier in the pipeline, Trivy catches everything in the built image.

**Q: Where does OWASP Dependency Check get its vulnerability data from?**
A: The NVD (National Vulnerability Database) maintained by NIST. It downloads a local copy of the database to the Jenkins agent and refreshes it periodically. No SaaS call per scan — it's a local database check.

**Q: The OWASP DC stage takes 40 minutes on first run. Why and how do you fix it?**
A: It downloads the NVD database (~500MB) for the first time. Since 2023, NVD rate-limits unauthenticated requests, causing very slow batch downloads. Fix: register for a free NVD API key and pass it via `--nvdApiKey`. Subsequent runs use the cached database.

**Q: How do you prevent the pipeline from continuing if a critical CVE is found?**
A: Use `dependencyCheckPublisher` with `failedTotalCritical: 1` — this marks the build FAILED if any Critical severity CVE is found. You can also set `failedTotalHigh` for a threshold on High severity findings.
