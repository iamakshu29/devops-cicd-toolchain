# 04 — Checkov: IaC Security Scanner

> Scans Terraform, K8s manifests, Dockerfiles, and CloudFormation for security misconfigurations.
> Catches the "I deployed an S3 bucket with public access" class of problems before they reach cloud.

---

## What It Is + Why It Matters

Checkov (by Bridgecrew/Palo Alto) is a static analysis tool for **Infrastructure as Code**. It reads your Terraform `.tf` files, Kubernetes YAML manifests, Dockerfiles, or Helm charts and checks them against hundreds of built-in security rules.

**What it catches:**
- S3 bucket with `acl = "public-read"` → fails CKV_AWS_20
- EC2 instance with no IMDSv2 enforcement → fails CKV_AWS_79
- K8s container running as root (no `runAsNonRoot`) → fails CKV_K8S_6
- Dockerfile running as root user (no `USER` directive) → fails CKV_DOCKER_2
- Security group open to `0.0.0.0/0` on port 22 (SSH) → fails CKV_AWS_25

**Why it runs at the top of the pipeline (before build):**
IaC problems are the cheapest to fix before cloud resources are provisioned. Running Checkov as the second stage means a Terraform misconfiguration is caught in 30 seconds — not after a resource is already live in AWS.

**No server, no database, no setup.** Checkov is just a Python CLI tool.

---

## How It Works

```
Jenkins Pipeline
      │
      ▼
Checkov CLI (installed on Jenkins agent via pip)
      │
      │  1. You point it at a directory: checkov -d terraform/
      │  2. Checkov reads all .tf files in that directory recursively
      │  3. Builds an abstract syntax tree of your infrastructure
      │  4. Runs each built-in check against the parsed resources
      │  5. Generates a report: PASSED, FAILED, SKIPPED checks per resource
      │  6. Exits with code 0 (all checks passed) or 1 (any check failed)
```

## Infrastructure Setup

No server. Install on the Jenkins agent:

```bash
pip3 install checkov
checkov --version
```

Or install in a virtual environment to avoid system Python conflicts:
```bash
python3 -m venv /opt/checkov-venv
/opt/checkov-venv/bin/pip install checkov
ln -s /opt/checkov-venv/bin/checkov /usr/local/bin/checkov
```

Verify it works:
```bash
checkov -d /path/to/terraform/dir
```

## Understanding the Key Flags

```bash
checkov \
  -d terraform/ \              # directory to scan (recursive)
  --framework terraform \      # which framework to scan: terraform | kubernetes | dockerfile | helm | all
  --check CKV_AWS_20 \         # run only specific check(s)
  --skip-check CKV_AWS_79 \    # skip specific check(s) — when you have accepted risk
  --soft-fail \                # always exit 0 even if checks fail (report but don't block)
  --output cli \               # output format: cli (default) | json | junitxml | sarif | github_failed_only
  --output-file-path ./reports/ \  # save report to file
  --quiet                      # show only failed checks (less noise)
  --compact                    # makes the scan output less verbose and easier to read.
```

**`--soft-fail` is the equivalent of Trivy's `--exit-code 0`** — you see the report but the build never fails. Use this when introducing Checkov to a repo that has existing findings you haven't triaged yet.

**`--framework` is important:** Without it, Checkov tries to detect the framework automatically, which can be slow and noisy if you have mixed content. Be explicit.

**`--compact`:** Only works when `--output cli`.

## The Jenkinsfile Stage

Checkov goes **near the top of the pipeline**, before the build — it scans source files, not build artifacts.

```groovy
// Generated by GitHub Copilot
stage('Checkov — IaC Scan') {
    steps {
        sh """
            checkov -d terraform/ \
              --framework terraform \
              --compact \
              --output cli \
              --output junitxml \
              --output-file-path ./reports/
        """
    }
    post {
        always {
            // Publish JUnit-format results so Jenkins shows pass/fail breakdown
            junit allowEmptyResults: true,
                  testResults: 'reports/results_junitxml.xml'
        }
    }
}
```

**Recommended stage order (Checkov goes before Build):**
```
Checkout → Checkov (IaC scan) → Build → SonarQube → ...
```

## Suppressing False Positives (Inline Skip)

Some checks flag things that are intentionally allowed in your design. You can suppress them inline in Terraform:

```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "my-log-bucket"

  # checkov:skip=CKV_AWS_20:Log bucket is intentionally public for cross-account log delivery
  acl = "public-read"
}
```

The comment must be exactly `# checkov:skip=CHECK_ID:reason`. The reason is mandatory — this creates a paper trail of why the check was skipped.

In a Jenkinsfile, you can also skip checks globally for a specific scan:
```bash
checkov -d terraform/ --skip-check CKV_AWS_20,CKV_AWS_79
```

**Do not blanket skip without reason.** Skipped checks without reasons are a security audit red flag.

## Verification

After the pipeline runs:
1. Jenkins console output shows something like:
   ```
   Passed checks: 42, Failed checks: 3, Skipped checks: 1
   ```
2. If you used `--output junitxml`, the JUnit results appear in Jenkins as a test report (Tests tab on the build page)
3. Each failed check shows the resource name, check ID, check description, and the file + line number

Example failed check output:
```
Check: CKV_AWS_20: "Ensure the S3 bucket has access control list (ACL) disabled"
  FAILED for resource: aws_s3_bucket.app_bucket
  File: /terraform/main.tf:12-18
```

## Common Errors + Debugging

### 1. Checkov finds hundreds of failures on first run
**Cause:** This is normal for existing Terraform that was written without security checks. The repo has accumulated technical security debt.
**Fix:** Use `--soft-fail` initially to get the report without blocking CI. Triage the findings, fix critical ones, and skip accepted risks with inline comments. Then remove `--soft-fail` once findings are under control.

### 2. `Error parsing Terraform file`
**Cause:** Checkov cannot parse `.tf` files that use Terraform modules with complex variable interpolations, or files with syntax errors
**Fix:** Run `terraform validate` first to ensure the Terraform is syntactically valid. For module parsing issues, run `terraform init` to download providers, then add `--download-external-modules true` to Checkov.

### 3. Pipeline fails on checks you expected to pass
**Cause:** Default Checkov checks are strict. For example, it may flag an EC2 instance for not having `monitoring = true` even if you do not need CloudWatch detailed monitoring.
**Fix:** Review the specific check ID in the output, read the Checkov docs for that check, and either fix it or skip it with a documented reason.

## Growing Pipeline Snapshot (After This Tool)

```groovy
pipeline {
    agent any
    environment {
        SONAR_PROJECT   = 'sample-app'
        NEXUS_REGISTRY  = 'nexus:8082'
        IMAGE_NAME      = "${NEXUS_REGISTRY}/sample-app"
        IMAGE_TAG       = "${env.BUILD_NUMBER}"
    }
    stages {
        stage('Checkout') {
            steps { git branch: 'main', url: 'https://github.com/your-org/sample-app.git' }
        }
        stage('Checkov — IaC Scan') {
            steps {
                sh 'checkov -d terraform/ --framework terraform --compact --soft-fail'
            }
        }
        stage('Build') {
            steps { sh 'mvn clean package -DskipTests' }
        }
        stage('SonarQube Analysis') {
            steps {
                withSonarQubeEnv('SonarQube') {
                    sh "mvn sonar:sonar -Dsonar.projectKey=${SONAR_PROJECT}"
                }
            }
        }
        stage('Quality Gate') {
            steps {
                timeout(time: 5, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }
        stage('OWASP Dependency Check') {
            steps {
                dependencyCheck additionalArguments: '--scan ./ --format XML',
                                odcInstallation: 'Dependency-Check'
                dependencyCheckPublisher pattern: 'dependency-check-report.xml',
                                         failedTotalCritical: 1
            }
        }
        stage('Docker Build') {
            steps { sh "docker build -t ${IMAGE_NAME}:${IMAGE_TAG} ." }
        }
        stage('Trivy — Image Scan') {
            steps {
                sh """
                    trivy image \
                      --exit-code 1 \
                      --severity HIGH,CRITICAL \
                      --ignore-unfixed \
                      ${IMAGE_NAME}:${IMAGE_TAG}
                """
            }
        }
    }
}
```

## Interview Questions

**Q: What does Checkov scan and when does it run in the pipeline?**
A: Checkov scans IaC files — Terraform, Kubernetes manifests, Dockerfiles, Helm charts — for security misconfigurations. It runs near the start of the pipeline, before the build, because it scans source files not build artifacts and IaC problems are cheapest to fix before cloud resources are provisioned.

**Q: What is the difference between Checkov and Trivy for IaC scanning?**
A: Both can scan IaC files. Checkov is purpose-built for IaC and has more checks and better framework support. Trivy also has `trivy config` for IaC scanning and is simpler if you are already using Trivy for image scanning. Many teams use both or consolidate on one.

**Q: A Checkov check is flagging something that is intentionally allowed in your design. How do you handle it?**
A: Suppress it inline in the Terraform file using `# checkov:skip=CHECK_ID:reason`. The reason is required and creates an audit trail. Avoid blanket skip flags on the command line as they apply to all resources and remove traceability.

**Q: How do you handle an existing Terraform codebase with 200 Checkov failures when introducing it to the pipeline for the first time?**
A: Start with `--soft-fail` so the pipeline reports failures without blocking CI. Triage the findings: fix critical misconfigurations first, add inline skips with justifications for accepted risks, and track remaining items as tech debt. Remove `--soft-fail` once the count is manageable and below your risk threshold.
